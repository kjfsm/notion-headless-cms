# nDash 製品ビジョン

## 北極星体験

> **編集者（非エンジニア）が Notion を保存すると、数十秒以内にサイトへ反映される。**
> エンジニアは初回セットアップ以降ノータッチ。誰もデプロイ・リビルド・静的生成を意識しない。

nDash は CMS ではない。CMS は Notion 自身であり、nDash は **Notion を本番サイトの管理画面に変えるライブ配信エンジン**である。

## 成功指標

| 指標 | 目標 |
|---|---|
| 反映時間（編集者が Notion を保存してからサイトに反映されるまで） | 既定で 1 分以内、webhook 連携時は数秒 |
| 鮮度のための手動配線手順 | **0**（webhook 登録は「秒に縮める」ための opt-in のみ） |
| 編集者のミスがサイト障害（5xx・白画面）になる回数 | **0**（fail-soft 保証） |
| エンジニアのセットアップ所要時間 | テンプレートから 10 分以内にライブ反映を体験 |

## 3 種類のユーザー

1. **編集者（非エンジニア）** — Notion しか触らない。下書き → プレビュー → 公開のすべてを Notion 内で完結する。ミスをしてもサイトは壊れず、問題は Notion 上でフィードバックされる
2. **エンジニア** — 初回にテンプレートからデプロイし、スキーマを TypeScript で定義する。以降はコンテンツ運用にノータッチ。型安全なデータアクセスと、フレームワークに自然に馴染む API を得る
3. **エージェント** — MCP / 機械可読 CLI 経由で nDash を操作する。Notion 公式 MCP（書く側）と nDash MCP（配信側）を組み合わせると、「記事を書いて公開し、反映を確認する」までがエージェントで完結する

## ポジショニング

| プロダクト | 編集体験 | 反映方式 | 型安全 | 立ち位置 |
|---|---|---|---|---|
| notion-to-md / react-notion-x | Notion | **ビルド時変換**（変換器のみ、配信は自前） | なし／弱い | 変換ライブラリ |
| 各種 SSG プラグイン（Astro/Next 向け Notion loader 類） | Notion | **ビルド時取り込み**（反映 = 再ビルド） | まちまち | ビルドパイプライン |
| Contentful / Sanity 等のヘッドレス CMS | 専用管理画面 | API + webhook | SDK 依存 | フル SaaS CMS |
| **EmDash**（Cloudflare） | **自前の管理画面・自前 DB** | サーバーレス配信 | TypeScript | フル CMS（WordPress 後継） |
| **nDash** | **Notion**（管理画面を作らない） | **ライブ反映**（リビルド不要） | **スキーマ駆動の型推論** | ライブ配信エンジン |

競合はすべて「ビルド時変換」側か「管理画面ごと自前」側におり、**「編集は Notion・反映はライブ・アクセスは型安全」の組み合わせは空白地帯**である。ここが nDash の存在理由。

### EmDash との関係

EmDash は Cloudflare が 2026 年に発表した Astro ベースのフルスタック TypeScript CMS（「WordPress の精神的後継」）。編集画面・DB・プラグイン基盤を自前で持つ。nDash は逆に**編集体験を Notion に完全委譲し、配信エンジンに徹する**。同じサーバーレス TypeScript 圏の補完関係にあり、設計面では次を参考にする:

- **agent-native**: エージェントが操作できる CLI、ビルトイン MCP サーバー、agent skills の同梱
- **ポータブルな抽象**: 全レイヤーを差し替え可能な抽象で組み、「Cloudflare（Workers）で最良、どこでも動く」
- **プラグインの capability 宣言**: プラグインがアクセス先を manifest で明示する方式（将来構想として ADR に記録）

名称 **nDash** も EmDash（em dash —）への対としての **en dash（–）+ Notion の "n"** に由来する。

## 体験の具体像

### 編集者の 1 日

1. Notion で記事を書く。status を「下書き」にしておく
2. Notion のページプロパティに自動で入る**プレビューリンク**を開き、実サイトの見た目で確認する
3. status を「公開済み」に変える → 1 分以内（webhook 設定済みなら数秒）にサイトへ反映される
4. slug を重複させてしまった → サイトは壊れず、Notion のコメントで「⚠ slug が重複しています」と通知される

### エンジニアの初日（とそれ以降）

1. テンプレートを選びデプロイ（Workers / Next.js / React Router / Astro / Hono）
2. `defineCollection` でスキーマを TypeScript で書く（codegen 不要。`ndash pull` で雛形生成も可）
3. `dash.posts.list()` / `dash.posts.get(slug)` で**完全にシリアライズ可能なプレーンデータ**を受け取り、loader からそのまま返す
4. 以降、コンテンツ運用で呼び出されることはない。スキーマ変更時だけ `ndash check` が CI で drift を教えてくれる

## Non-goals（やらないこと）

1. **静的サイト生成・ビルド時取り込み経路は提供しない。**
   検討の上で棄却した: 静的経路はランタイム依存ゼロ・rate limit 無縁という利点があるが、北極星（編集者がデプロイ・リビルドを意識しない）と相反する。「反映 = 再ビルド」の世界には既に Astro Content Collections 等の優れた解があり、nDash が参入する理由がない。ライブ反映に集中する
2. **管理画面・編集 UI を自作しない。**
   CMS は Notion 自身。編集体験の改善はすべて「Notion 側に情報を書き戻す」形（プレビューリンク・コメント通知）で行う。EmDash のように管理画面を持つ方向には行かない
3. **非公式 Notion API に依存しない。**
   react-notion-x 系が依存する非公式 API（recordMap）は破壊リスクが大きい。公式 API のみを使い、その制約（rate limit 3req/s・再帰 blocks 取得）は freshness ループと PortableContent キャッシュで吸収する
4. **汎用マルチソース CMS を目指さない。**
   旧 nhc は DataSource 抽象で Contentful 等への拡張可能性を持たせたが、抽象の維持コストが Notion 特化の体験改善を妨げた。nDash は Notion 専用。内部レイヤーの分離（architecture.md）は保つが、公開 API でマルチソースを約束しない
